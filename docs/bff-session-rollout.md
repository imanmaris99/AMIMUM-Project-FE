# Customer FE BFF session rollout gates

The customer frontend now sends backend API requests through same-origin `/api/backend/*` routes. These routes use the server-only `BACKEND_API_URL`; `NEXT_PUBLIC_API_BASE_URL` / `NEXT_PUBLIC_API_URL` fallbacks are permitted only outside production. The production hosting environment must set `BACKEND_API_URL` to the backend origin before deploying. No hosting provider or production origin was verified in this local task.

Login and Google login are proxied through `/api/auth/login` and `/api/auth/google-login`. Backend bearer credentials are stored only in the `amimum_session` HttpOnly cookie; UI metadata is not an authentication credential. Cached UI metadata can briefly make a client-side guard look authenticated until session bootstrap completes, but every protected backend request still requires the server-side cookie. Cookie settings are `Path=/`, host-only (no Domain), `SameSite=Lax`, and `Secure` in production. Unsafe BFF requests require the exact same-origin `Origin` and a matching `X-CSRF-Token`/readable host-only CSRF cookie.

There is no backend refresh or revocation endpoint. Every auth-cookie transition (password/Google login, logout, and CSRF initialization) requires the browser Web Locks API (`navigator.locks`) and is serialized with the shared `amimum-auth-cookie-transition` lock across tabs. There is deliberately no tab-local fallback: browsers without Web Locks fail transitions closed, so login/Google login is not submitted and logout still clears local UI metadata immediately but reports server-cookie deletion as unsuccessful. The login UI asks customers to update/use a supported current browser. Rollout browser compatibility must therefore be checked against the actual customer browser/device matrix in a secure context; require a current browser with Web Locks support and test the unsupported path. Concurrent same-tab logout calls share one request; the CSRF endpoint reuses an existing valid cookie. Stale bootstrap, profile-hydration, and 401 responses are revision-checked against a shared localStorage generation; automatic 401 handling clears only local session metadata and deliberately does not emit a cookie-deletion response that could erase a newer login. Therefore an invalid upstream cookie can remain until explicit logout, a later successful login, or its expiry. Cookie deletion remains best-effort and is only confirmed when the request succeeds. The upstream JWT also cannot be revoked and remains usable until its own expiry. Cookie lifetime is bounded by JWT `exp`. Tokenless/opaque upstream login responses do not establish a valid cookie session.

Before production rollout, verify on the actual deployment target: (1) server runtime supports Next.js Route Handlers and outbound backend access, (2) `BACKEND_API_URL` is configured and HTTPS, (3) the canonical customer site origin is the only served origin for these routes, and (4) all required API paths/methods are represented in the BFF allowlist. No production deployment, authenticated login, or backend mutation was performed here.

## Local-only integration evidence

The optimized Next.js build was exercised against an ephemeral HTTPS dummy upstream before the latest stale-response hardening (no real account or database): dummy login returned 200 without exposing its test JWT in the JSON response, `document.cookie`, or `localStorage`; the HttpOnly session restored the customer profile page at a 390×844 viewport. That earlier probe confirmed upstream 503 retained the cookie, while its then-current 401 behavior cleared it. The current implementation intentionally changed automatic 401 handling to preserve the cookie against stale-response races; this changed behavior has unit/source gates but the browser integration probe has not yet been repeated. This is local-only evidence; it does not verify production hosting, real backend auth, provider email, or a live deployment.
